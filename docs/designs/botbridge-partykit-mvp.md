## Problem Statement
People who use local agents (Grok, Antigravity, Claude Code) want to work together in a shared space, but there is no native way to connect independently owned bots so they can collaborate without conflicting and overwriting each other's code.

## What Makes This Cool
You are the conductor of an AI orchestra. Two specialized bots talk to *each other*, align on a plan in a shared CRDT memory space, and execute together seamlessly without chaotic file thrashing.

## Constraints
- Needs to be fast to build and shareable.
- Must handle real-time sync without requiring a massive backend setup.
- Avoids the black-box overwrite paradigm.

## Premises
1. **Coordination over Chaos:** Agents need a shared CRDT memory to plan and lock resources before acting.
2. **Stateless Relay:** The bridge is a fast message bus/CRDT sync layer, aligned with MCP's shift to statelessness.
3. **Distribution:** Web-hosted for easy connection, allowing local bots to connect via WebSocket.

## Cross-Model Perspective
**The "Spatial Memory" Canvas:** The Claude subagent suggested making the CRDT memory a literal 2D canvas (like tldraw) where agents and humans can see a spatial representation of the plan before execution. 
**Insight:** What excites the builder is the thrill of being a conductor of an AI orchestra.
**Prototype Suggestion:** Build a PartyKit + Yjs backend with an MCP translation layer.

## Approaches Considered
### Approach A: The PartyKit JSON-RPC Bridge
Summary: A lightweight PartyKit server holding a Yjs document. A local MCP wrapper translates agent tool calls into Yjs updates. Memory is a shared JSON object.
Effort: (human: ~1 day / CC: ~1 hr)
Risk: Low
Pros: Fastest path to working handshake; outsources socket hosting/conflict resolution.
Cons: Doesn't give human observers a great visual way to watch memory evolve initially.

### Approach B: The Agent Orchestrator with Central Locking
Summary: Custom Next.js backend with Redis, providing formal API for file locks and an approval dashboard.
Effort: (human: ~4 days / CC: ~3 hrs)
Risk: Med
Pros: Robust for enterprise use; fine-grained access control.
Cons: Massive scope creep for a weekend build.

### Approach C: The Spatial "Tldraw" Canvas
Summary: Agents interact with tldraw's multiplayer engine to place text nodes and connectors.
Effort: (human: ~2 days / CC: ~2 hrs)
Risk: High
Pros: Incredible demo appeal.
Cons: Hard for LLMs to map text plans into clean 2D coordinates without overlap.

## Recommended Approach
Approach A: The PartyKit JSON-RPC Bridge. It gets to the magic "two bots talking" moment this weekend using battle-tested CRDT infrastructure.

## Open Questions
- How exactly do we map the MCP tool calls (`write_shared_memory`, `acquire_lock`) into Yjs transactions efficiently?
- What is the easiest way to give humans a read-only window into the raw JSON CRDT state in the MVP?

## Success Criteria
Two local agents (e.g., Antigravity and Grok) connected to the same PartyKit room URL, successfully completing a handshake where Agent A writes a plan to shared memory and Agent B reads and acknowledges it.

## Distribution Plan
The PartyKit server deployed to Cloudflare. Users configure their local agents to connect to the provided wss:// URL as an MCP Server.

## Next Steps
1. Initialize a generic PartyKit server (`server.ts`) that hosts a Yjs document with a `state` map and a `locks` set. Deploy it.
2. Build a local TypeScript MCP Server that takes a room URL, connects via WebSocket, and exposes `read_shared_memory()`, `write_shared_memory(key, value)`, and `acquire_lock(resource_name)`.
3. Boot up two local agents pointing to the same room URL and watch them handshake.
